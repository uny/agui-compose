# 8. Executing a tool on the client

Date: 2026-09-13

## Status

Accepted.

## Context

A frontend tool is one the agent calls and the client runs: the server streams `TOOL_CALL_START`,
`TOOL_CALL_ARGS` and `TOOL_CALL_END` as it does for any tool, ends the run, and expects the result
to come back **in the next run's input** as a `ToolMessage` -- the protocol has no other channel
for it. `agui-core` already folds the call into a `ToolCallPart` and draws it `AWAITING_RESULT`;
nothing in this repository executed anything or sent anything back. Everything above chat that this
library is aimed at -- generative UI, A2UI, human-in-the-loop -- enters through a frontend tool, so
this is the seam the rest hangs from.

Upstream's `kotlin-tools` 0.4.1 has most of it, measured with `javap` over the published jar
because the source is not what ships:

- `ToolRegistry` / `ToolExecutor` / `AbstractToolExecutor`: a tool is a `Tool` declaration plus a
  suspending `execute`, with validation, a timeout and per-tool stats around it.
- `ToolExecutionManager(registry, handler).processEventStream(events, threadId, runId)` is a
  **flow transformer**. It passes every event through unchanged, assembles a call from its three
  events, and on `TOOL_CALL_END` launches a job in a `coroutineScope` of its own that executes the
  tool and hands the resulting `ToolMessage` to a `ToolResponseHandler`. On `RUN_FINISHED` or
  `RUN_ERROR` it joins every job before the stream completes. A call whose tool the registry does
  not hold is reported as `Failed("Tool not found (server-handled)")` on the manager's own event
  flow and **no message is sent** -- so backend tools pass through untouched. An executor that
  throws becomes a `ToolMessage` whose `content` says so; the manager never sets
  `ToolMessage.error`.
- The handler is called from that job, on whatever dispatcher the collector is on, while the run's
  stream is still being collected.
- `ClientToolResponseHandler(HttpAgent)`, upstream's handler, answers a tool by calling
  `agent.runAgentObservable(RunAgentInput(messages = listOf(toolMessage)))` **inside**
  `sendToolResponse` and collecting the result there. That is a second run started from within
  the first, with a history of one message, whose events go nowhere this library can see -- and
  it takes none of the turns [decision 5](0005-running-the-upstream-agent.md) made runs on one
  session take.

Two facts about the surrounding pieces bear on the shape:

- `kotlin-client`'s state layer (`defaultApplyEvents`) folds `TOOL_CALL_*` into the assistant
  message's `toolCalls` and `TOOL_CALL_RESULT` into a `ToolMessage`, inline as the stream is
  collected. So by the time a run has ended, `agent.messages` holds the call the way the protocol
  wants it sent back, and a `ToolMessage` appended after it is a history a server accepts.
  Measured by a test rather than assumed.
- `UiTranscriptReducer` is fed from one coroutine and says so.

## Decision

`AgentSession` takes an optional `ToolRegistry`. With one:

1. **Every run declares the registry's tools**, after the caller's `RunAgentParameters.tools`,
   through `run` and `send` alike. Neither list is deduplicated. A run's id is generated by the
   session rather than left to the agent, because the manager wants it before the agent is asked.
2. **Upstream's manager is inserted between the agent's stream and the reducer** -- the one place
   that keeps the collector single and the runs serial. It is reused rather than rewritten
   because the event assembly, the timeout, the not-found pass-through and the executor contract
   are all things a consumer's tools will be written against.
3. **The `ToolResponseHandler` is this library's, and it does one thing: put the message on a
   channel.** The collecting coroutine drains the channel before each event and once more after
   the stream ends, folds each result into the transcript as a `TOOL_CALL_RESULT` -- the same way
   a client-side failure is folded as a `RUN_ERROR` in decision 5 -- and keeps it to send. The
   ordering is safe: the manager emits `TOOL_CALL_END` downstream before it starts the job, and
   `emit` returns only after the collector has folded it, so no result can land ahead of its call.
4. **A finished run with results to send is answered by a run of its own**, started by the same
   code under the same lock: the thread's history with the results appended, the same `tools`,
   `context` and `forwardedProps`, a new run id. That run may call a tool too, and is answered the
   same way, until one does not. `run` and `send` suspend for the whole exchange and return the
   state the *last* run ended in. An interrupted run is a finished run: a tool this client executed
   is the answer the interrupt was waiting on. A tool the registry does not hold is left where the
   protocol leaves it, which is also where a human-in-the-loop approval sits.
5. **A result whose run did not finish is kept, not dropped.** A `RUN_ERROR`, a throw, or a
   cancellation while a tool was executing leaves the result folded on screen and held by the
   session; it goes out ahead of the next `run` or `send`. The alternative -- dropping it -- leaves
   `agent.messages` holding a call with no result, and that is a history most model backends
   refuse to continue. `setMessages` is protected, so the session cannot repair the agent's copy;
   carrying the message to the next input is the repair.

`agui-sample` executes one tool, upstream's own `change_background`, and paints what it is sent.
Verified against `server-starter-all-features`' `/agentic_chat`, which calls that tool on the turn
`tool` and answers the result with `background changed ✓` -- the whole loop, no model, no key.

## Consequences

- `RunState.Finished` is the run's verdict and not the turn's. A transcript reads `Finished` while
  a tool is still executing and again between a run and the run that answers it; a UI gating on
  "the agent is done" gates on the suspend call returning. The KDoc on `Finished` says so, and the
  sample gates that way.
- The session's constructor changed shape -- the parameter is last and defaulted, so every
  existing call still compiles, but the JVM constructor is a new one. Nothing is published yet
  (decision 7's status note stands) and the ABI dumps are updated.
- `kotlin-tools` is now declared by `agui-agent` as `api`, though it arrived through
  `kotlin-client` already: the catalog's own rule is that a module whose public signatures name a
  type declares the artifact.
- A server that calls a registered tool on every run, whatever it is sent, is answered on every
  run; there is no cap. That is the protocol's loop, a model that stops calling tools ends it, and
  cancelling the coroutine ends it otherwise. A scripted server that never stops is a server to
  fix.
- Not decided here: what a *pending approval* looks like in the model. `ToolCallStatus` has no
  "awaiting a human" state, and adding one is an `agui-model` ABI change that should follow a
  measurement of what upstream's interrupt outcome actually carries. Human-in-the-loop is
  reachable today -- the run stops interrupted, the client `send`s or `run`s when it is ready --
  but not drawn as such.
